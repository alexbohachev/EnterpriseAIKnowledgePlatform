# Етап 1. Технічне завдання та архітектура

**PRD + SRS  |  Межі MVP  |  C4 Level 1–2  |  Початкові ADR**

Версія 0.1  •  16 листопада 2026  •  Статус: базовий дизайн, реалізацію ще не розпочато

Призначення: проєктування захищеної локальної платформи для аналізу корпоративних документів із GraphRAG та перевіркою прав доступу.

Основне джерело вимог: завантажене завдання OTUS «project .txt». Уточнення щодо дозволених альтернатив: консультація курсу №33. Технічні рішення та цільові метрики нижче є проєктними пропозиціями, а не підтвердженими результатами тестування.


### Що підготовлено на цьому етапі

- PRD: проблема, користувачі, цінність, сценарії, критерії успіху.

- SRS: функціональні та нефункціональні вимоги з ідентифікаторами й перевірками.

- Межі MVP, інтерфейси, модель загроз і критерії приймання.

- C4 Level 1 (System Context) та C4 Level 2 (Container) з окремими файлами схем.

- Попередній стек, ADR-рішення, список ризиків і план наступної реалізації.

Позначення: [OTUS] — прямо випливає з письмового завдання; [ПРОПОЗИЦІЯ] — рішення для MVP; [ВІДКРИТО] — потрібно підтвердити фактичними тестами або вибором середовища.

| Поле | Значення |

### 1.1. Що саме вимагає OTUS

- Проєктування та MVP End-to-End конвеєра для неструктурованих корпоративних документів, сканів, складних PDF і графового аналізу знань.

- Закритий контур; локальне LLM Serving; Vector Database; оркестрація зі станом; observability; контроль доступу до чанків/вузлів графа.

- Архітектурний пакет із C4, Deployment, Sequence, ER та Data Flow; письмово задано до 40% ваги оцінювання саме для архітектури.

- Для випуску: monorepo, коротка демонстрація, навантажувальний звіт і перевірка відсутності міжкористувацьких витоків.


### 1.2. Узгодження неоднозначностей

Письмовий документ прямо вказує GraphRAG як обов’язковий для цього конкретного варіанта та забороняє простий векторний пошук як єдину реалізацію. В усній консультації №33 викладач описав більш гнучкі варіанти для власних тем і альтернативних Advanced RAG рішень. Щоб не ризикувати відповідністю саме цьому письмовому завданню, у нашому MVP залишаємо і векторний індекс, і граф знань; будь-який інший варіант потребуватиме окремого узгодження.

Air-gapped у нашій пропозиції означає нуль зовнішніх runtime API та вихідного трафіку. Артефакти моделей і Docker-образів переносяться в закритий контур завчасно. Реальна сертифікація відповідності законодавству/політикам замовника не входить до MVP і потребує окремої перевірки.


## 2. PRD — Product Requirements Document


### 2.1. Проблема та цінність

Корпоративні знання розпорошені в довгих PDF, текстових інструкціях, сканах і документах зі складною структурою. Звичайний пошук за ключовими словами не завжди бачить зв’язки між фактами, а вільна генерація LLM може давати недоведені відповіді. Потрібна керована система, що знаходить підтвердження в дозволених документах, використовує графові зв’язки та не відкриває стороннім користувачам конфіденційний вміст.


### 2.2. Користувачі й ролі

| Роль | Потреба | Доступ |

| --- | --- | --- |

| Співробітник (Reader) | Запитувати, знаходити відповіді з джерелами | Тільки документи, на які є ACL |

| Власник документа (Owner) | Завантажувати та призначати доступ | Лише власні / делеговані документи |

| Адміністратор (Admin) | Контролювати доступ, індексацію та аудит | Адміністрування згідно з політикою |

| Оператор (Ops) | Слідкувати за метриками та інцидентами | Мінімально необхідний технічний доступ |




### 2.3. Ключові користувацькі сценарії

| ID | Сценарій | Очікуваний результат |

| --- | --- | --- |

| UC-01 | Owner завантажує PDF зі списком дозволених користувачів | Завдання індексації; збережені оригінал, метадані, ACL |

| UC-02 | Reader запитує факт із дозволеного документа | Відповідь із назвою документа та сторінкою/фрагментом |

| UC-03 | Reader ставить multi-hop запитання про два пов’язані об’єкти | Retrieval звертається до векторного та графового індексів |

| UC-04 | User B намагається дізнатися вміст секретного документа User A | Відмова / відсутність секретних фрагментів у контексті й відповіді |

| UC-05 | Admin змінює ACL документа | Наступний запит використовує актуальні права, індекси не обходять перевірку |

| UC-06 | LLM не знайшла підтвердження | Коректне «недостатньо даних» без вигаданих посилань |




### 2.4. Продуктові результати — як вимірюємо

| Показник | Пропозиція для MVP | Перевірка |

| --- | --- | --- |

| Якість пошуку | Recall@5 ≥ 0.80 на ≥ 30 вручну перевірених запитаннях | Офлайн evaluation dataset [ВІДКРИТО] |

| Підтвердженість | ≥ 85% відповідей мають коректні посилання на дозволені джерела | Ручна перевірка за рубрикою [ВІДКРИТО] |

| Ізоляція даних | 0 витоків у ≥ 50 негативних ACL-тестах | Автоматичні security тести [ОБОВ’ЯЗКОВО для MVP] |

| Операційність | Наявні traces і метрики latency/RPS/tokens | Демонстрація dashboard + tracing |

| Швидкодія | Зафіксовані p50/p95 latency, throughput, VRAM, конфігурація | Навантажувальний звіт; пороги визначити після сайзингу |



Наведені цифри — стартові критерії, запропоновані нами для самоперевірки, не норматив OTUS і не обіцянка продуктивності. Перед захистом зафіксуємо baseline, методику, обладнання та результати.


## 3. MVP — що входить і що відкладено


### 3.1. Входить у MVP (Must Have)

- Завантаження текстових і сканованих PDF; для сканів — локальний OCR, без зовнішніх сервісів.

- Розбиття тексту на чанки з метаданими документа, сторінки, owner, ACL, версії індексації.

- Локальне створення embeddings та індексація в Qdrant.

- Мінімальний knowledge graph (Document, Chunk, Entity) у Neo4j і зв’язки PART_OF / MENTIONS / RELATED_TO.

- Пошук з поєднанням векторних кандидатів і графового розширення; фільтрація доступу перед формуванням prompt.

- LangGraph або сумісна state machine для контрольованих станів: authorize → retrieve → validate → generate / abstain.

- Локальна інструкційна LLM, цитування джерел, відповідь «немає даних», audit ID для запитів.

- Два тестові користувачі з різними ролями; перевірка доступу до документів/чанків/графа.

- Відтворюваний запуск Docker Compose, тестовий набір, логи/метрики/трейси, короткий звіт по навантаженню.


### 3.2. Не входить у перший MVP (Later / Out of Scope)

- Навчання або fine-tuning фундаментальної моделі; інтеграції зі зовнішніми хмарними LLM API.

- Повний аналіз креслень, складних таблиць і мультимодальна семантика всіх типів файлів (спершу OCR + текстові PDF).

- Продукційна інтеграція з ERP/CRM та промисловим корпоративним SSO; підтримка кількох незалежних тенантів.

- Багатовузловий Kubernetes/HA/DR, SLA 99.9%, автоматична еластична GPU-оркестрація.

- Публічний SaaS, мобільний клієнт, комерційне тарифікування, юридична атестація безпеки.

Примітка щодо мультимодальності: завдання згадує скани, креслення та складні PDF. У першому MVP перевіряємо end-to-end OCR на сканованих PDF; підтримку специфічних графічних креслень чесно зазначаємо як наступну ітерацію або розширення перед захистом, якщо буде потрібна для оцінювання.


### 3.3. Межі експерименту

| Параметр | Стартове значення [ПРОПОЗИЦІЯ] |

| --- | --- |

| Корпус | 30–100 тестових документів із дозволеним для використання вмістом |

| Тип файлів | PDF із текстовим шаром + ≥ 5 сканованих PDF |

| Користувачі | Reader A, Reader B, Owner, Admin; окремі ACL для щонайменше 5 документів |

| Мова | Українська/російська як бізнес-орієнтир, залежно від локальної моделі; тестувати фактично |

| Середовище | Один сервер / робоча станція з локальним GPU, характеристики TBD |

| Обсяг графа | 3 типи вузлів; десятки/сотні сутностей, не мільйони |

| Реліз | MVP без обіцянки промислової HA/DR |




## 4. SRS — Software Requirements Specification


### 4.1. Функціональні вимоги

| ID | Функція | Вимога | Критерій приймання |

| --- | --- | --- | --- |

| FR-01 | Ідентифікація та авторизація | Всі API запити прив’язані до user_id/roles; запити без токена відхиляються. | 401/403 на незареєстровані й неавторизовані запити. |

| FR-02 | Приймання документів | Owner може завантажити локальний PDF із метаданими, власником і ACL. | POST повертає job_id; документ доступний для status/read. |

| FR-03 | Обробка та OCR | Для текстових PDF — витяг тексту; для сканів — локальний OCR; збереження номера сторінки. | Сканований PDF стає доступним пошуку; сторінку можна відкрити. |

| FR-04 | Індексація векторів | Ембеддинги утворюються локально і зберігаються з doc_id, chunk_id, ACL/version. | Знаходимо потрібні чанки в офлайн наборах. |

| FR-05 | Побудова графа | Вузли Document, Chunk, Entity та типізовані ребра створюються з provenance. | Є хоча б 1 перевірений multi-hop кейс з графовим шляхом. |

| FR-06 | Гібридний retrieval | Кандидати з Qdrant + Neo4j поєднуються; джерела і права зберігаються. | Результат містить doc_id, chunk_id, path, citation. |

| FR-07 | Генерація відповіді | Локальна LLM відповідає лише на підставі дозволених джерел і дає цитати. | Без джерел — abstain, без фальшивих цитат. |

| FR-08 | Доступ до даних | ACL перевіряється до retrieval, під час graph expansion і перед LLM контекстом. | User B не отримує жодного chunk/graph path User A. |

| FR-09 | Stateful orchestration | LangGraph керує кроками, умовами та обробкою помилок. | State transitions трасуються; відсутній лише лінійний script. |

| FR-10 | Керування індексацією | Admin бачить job status, може повторити ідемпотентну індексацію. | Повтор не створює дублікати без зміни версії. |

| FR-11 | Аудит і діагностика | Кожен запит має request_id, trace_id, model_version, status без секретного тексту у звичайних логах. | Метрики і трейс демонструються локально. |

| FR-12 | Офлайн режим | Сервіс не залежить від зовнішніх хмарних inference/embedding API. | Egress блокований; повний тестовий сценарій працює. |

| FR-13 | Оцінювання якості | Є evaluation corpus і скрипт для retrieval/grounding/security тестів. | Генерується відтворюваний звіт із конфігурацією. |

## 5. C4 Level 1 — контекст системи

На рівні C1 показано головну цінність платформи та зовнішніх акторів: працівник, адміністратор, корпоративний identity provider, ERP/CRM та внутрішні сховища. Для першого MVP інтеграція ERP/CRM не реалізується — замість неї є ручне завантаження документів у закритому контурі.

![Рис. 1. C4 L1 — контекст: користувачі, EAKP, джерела даних та внутрішня IAM.](../diagrams/c4_level1.png)



### Ключові межі довіри C1

- Зовнішній відносно EAKP користувач не має прямого доступу до сховища файлів, Qdrant чи Neo4j; доступ можливий тільки через API з перевіркою прав.

- Для MVP може застосовуватися тестовий локальний identity provider; у промисловій системі інтеграція з корпоративним OIDC/SSO.

- ERP/CRM — лише внутрішні джерела майбутнього read-only імпорту; жоден connector не запускає неконтрольованих зовнішніх API викликів.


## 6. C4 Level 2 — контейнери

Розділяємо Control Plane (авторизація, політики, оркестрація, керування ingestion) та Data Plane (дані, індекси, локальні моделі). Це логічний поділ відповідальності, а не твердження, що сервіси вже розгорнуті окремо. Фізичні мережеві зони й GPU-розміщення будуть описані на наступному етапі у Deployment Diagram.

### 6.2. Потік запиту — базовий sequence

1. Клієнт надсилає запит з access token → FastAPI перевіряє автентичність і rate limit.

1. Orchestrator перевіряє політики, нормалізує запит та ініціює retrieval.

1. Retrieval Service обмежує кандидатів ACL до пошуку (де підтримується), перевіряє doc_id/chunk_id після пошуку та при обході графа.

1. Кандидати з Qdrant і Neo4j зливаються; усі шляхи та цитати проходять фінальну authorization перевірку.

1. Тільки дозволені фрагменти потрапляють у контекст локальної LLM; генерація містить evidence/citations або abstain.

1. Відповідь з trace_id повертається користувачу; аудит зберігає метадані, але не повний текст секретних документів.


### 6.3. Потік ingestion

Owner → API (перевірка ACL) → Object Storage (оригінал) + PostgreSQL (job, метадані) → Ingestion Worker (PDF parser/OCR) → chunking + provenance → local embedding → Qdrant + entity/relation extraction → Neo4j. При зміні ACL система перевіряє актуальні права на кожному запиті; eventual consistency індексів не повинна відкривати старі права.


## 7. Security-by-Design і перевірюваність


### 7.1. Схема авторизації

Дозвіл визначається через owner, групи та explicit access grants. Принцип: deny-by-default. API не довіряє user_id у тілі запиту; ідентичність походить тільки з перевіреного токена. Кожен chunk зберігає doc_id; кожен Entity та graph edge має provenance (document_id / chunk_id), щоб графовий шлях можна було перевірити за ACL. Спільні entity вузли не повинні розкривати назви або зв’язки заборонених джерел.

| Ризик | Захист у MVP | Тест |

| --- | --- | --- |

| Indirect prompt injection у PDF | Документ — недовірене джерело; instructions з OCR не виконуються; інструменти allowlist | Документ містить «ігноруй правила»; агент не змінює policy |

| Витік через векторний пошук | Пошук із ACL prefilter де можливо + postfilter перед prompt | User B не бачить секретний chunk у retrieve |

| Витік через граф | Перевірка provenance/ACL кожного вузла/ребра/шляху | Graph expansion не видає Entity із забороненого джерела |

| Неправильне цитування | Підтверджена сторінка/chunk; abstain без доказів | Цитати завжди існують і доступні user |

| Витік через telemetry | Редація логів, агреговані метрики, захищені трейси | Синтетичний PII відсутній у логах |

| Викрадення ключів / egress | Offline режим, без секретів у Git, локальний registry | Blocked outbound, secret scan |




### 7.2. Acceptance/security test suite — обов’язково

- AT-01: Reader A отримує відповідь з дозволеного документа й коректною цитатою.

- AT-02: Reader B, не маючи ACL, не отримує секретного фрагмента через векторний retrieval.

- AT-03: Reader B не отримує секретну назву/зв’язок через graph traversal та graph summary.

- AT-04: зміна ACL із allow на deny блокує доступ до наступного запиту навіть до повної переіндексації.

- AT-05: запит із підробленим user_id / role у JSON не підвищує права.

- AT-06: інструкція всередині PDF не призводить до запуску інструмента чи обходу guardrails.

- AT-07: документ без підтвердження дає abstain; не видаються вигадані сторінки.

- AT-08: при заблокованому egress ingestion → query → відповідь виконується локально.

- AT-09: звіти містять p95 latency, RPS/throughput, використання VRAM, версії моделі та обладнання.

- AT-10: повторна обробка одного PDF за тим самим checksum не створює зайві вузли/чанки.


## 8. Технологічні рішення й ADR

| ADR | Рішення [ПРОПОЗИЦІЯ] | Причина і trade-off |

| --- | --- | --- |

| ADR-0001 | Offline-first: локальне serving та індекси | Відповідність закритому контуру; складніші оновлення моделей/образів |

| ADR-0002 | GraphRAG = Qdrant + Neo4j | Виконує конкретний письмовий варіант OTUS; дорожче підтримувати дві бази, ніж одну |

| ADR-0003 | LangGraph та policy gates | Прозорий стан/умови; більше складності, ніж звичайна функція |

| ADR-0004 | PostgreSQL job table у MVP | Не потребує Kafka на малому навантаженні; межі масштабування відомі |

| ADR-0005 | Docker Compose перед Kubernetes | Швидко показати end-to-end; HA та auto-scale залишаються поза MVP |




### 8.1. Окрема примітка щодо LLM Serving

Письмовий текст пропонує vLLM / SGLang / TGI, квантовані локальні моделі й оптимізацію KV-cache. Остаточний вибір engine, моделі, формат квантування (AWQ / інші сумісні формати) та контекстне вікно залежатимуть від конкретного GPU і підтримки модель/рушій. Не варто припускати, що кожен формат квантованих ваг однаково підтримується кожним рушієм. До експериментального заміру залишаємо в ADR два кандидати, не фіксуємо неперевірені числові характеристики.


### 8.2. Чому не cloud-first і не лише vector search?

Cloud inference API суперечить письмовій вимозі автономного контуру. Лише vector search не демонструє графові зв’язки та окремо визначений GraphRAG у заданій темі. При цьому GraphRAG має реальні компроміси: складність entity extraction, latency, consistency/ACL і потреба в окремих графових тестах. Саме ці недоліки потрібно чесно показати в захисті.

### 9.2. Відкриті питання перед кодом

- Яке фізичне обладнання (GPU VRAM, RAM, CPU, диск) реально доступне? Від цього залежить розмір/engine LLM і p95.

- Чи дозволено зберігати тестові PDF, чи потрібен повністю синтетичний корпус?

- Чи очікується OCR лише текстових сканів, чи також критично потрібне розпізнавання креслень?

- Яка рольова політика і чи потрібна перевірка груп із реального корпоративного IdP?

- Які мови документів/запитів та допустима затримка для демонстрації?

- Чи буде цільовий захист саме за письмовим GraphRAG-варіантом? Цей дизайн виходить із відповіді «так».

- Чи потрібно документувати окремі вимоги законодавства конкретної юрисдикції? Це за межами технічного MVP.
